# FEAT-009 — Combat setup, result and event contract

**Status:** Version-one sandbox boundary implemented; typed event and reusable NPC integration remain proposed.
**Branch:** feature/standalone-combat-lab · **Reviewed:** 2026-11-12

## Purpose
Provide a stable combat protocol that later narrative, NPC and automated-test systems can consume without depending on a campaign engine.

## Human instructions
Approve contract evolution, error handling, outcome taxonomy and eventual NPC data ownership before integration elsewhere.

## AI agent instructions
Implement only bounded changes, maintain deterministic output and prohibit narrative or campaign dependencies in CombatEngine.

## Current implementation
- `CombatSetup` is a version-one Dictionary with `schema_version: 1`, `seed`, `party`, `encounter`, and lab metadata; it is constructed from known test fixtures and passed to `CombatEngine.start_from_setup(setup)`.
- The engine validates schema and basic party/enemy collection shape, then builds isolated actor instances. It never calls narrative code.
- `CombatResult` is stored as `user://combat_lab_last_battle.json` with the exact initial setup and a result containing outcome, rounds, combatant states, positions, resources, equipment/inventory snapshots and event list.
- The lab returns `xp=0`, `gold=0`, `loot=[]` explicitly. Awards are never generated by the combat engine.

## Proposed hardening
- Add explicit `CombatantDefinition` vs `CombatantInstance` records, validated stable IDs and level/resource policies. Do not couple to temporary hero IDs.
- Add `event_id`, `action_id`, `actor_id`, `target_id`, `kind`, `round` and effect payload to resolved events. Keep prose/audio optional renderings, not the source of truth.
- Support outcome taxonomy: win/loss/surrender/escape/objective achieved rather than victory by annihilation only.
- Support different enemy archetypes in one encounter and future morale profiles; no Hesk-specific logic.
- Add result contract for timed statuses, item/resource consumption and encounter-local NPC identity when an external registry is eventually available.
- Introduce validation tests for malformed IDs, counts, unsupported mechanics and deterministic seed replay; plan migration/versioning before changing the format.

## Registry boundary (future, separate branch)
The combat lab does NOT own persistent NPC identity, whereabouts, trust, quests or loot policy. Later an external EncounterOrchestrator may materialise combatants from an NPC register and commit outcomes once, while the battle simulation remains agnostic.

## Acceptance / verification
- Current: headless Combat Lab configuration and result persistence tests, no campaign code.
- Future: exact schema validation, typed event sequence, stable results across replay, no duplicated state mutations, human approval before public contract promotion.

## Exclusions
Campaign state migration, narrative decisions, NPC registry implementation, full level-2 mechanics and animations.

## Future footprint contract (FEAT-017)

Generic combatant definitions will need explicit **size category and authoritative occupied-square footprint**, separate from artistic texture dimensions and with a versioned migration policy. Proposed instance position remains a top-left grid anchor; existing single-square actors must default to 1×1. Structured combat events should include suitable snapshots of actual source/impact geometry for projectiles and animation. See [FEAT-017](FEAT-017-multi-tile-creatures.md). These are **proposals**, not existing schema fields.
